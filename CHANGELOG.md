# Changelog

All notable user-facing changes to ZynForge Recording are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versioning targets [Semantic Versioning](https://semver.org/spec/v2.0.0.html), though the project is pre-1.0 and minor / patch boundaries are pragmatic.

## How this file is maintained

- Add new entries under `## [Unreleased]` as you ship changes.
- When cutting a release, rename the section to `## [X.Y.Z] – YYYY-MM-DD` and start a fresh `## [Unreleased]`.
- Use the categories below. If none apply, the entry probably isn't user-visible and doesn't belong here.
- Keep entries terse but specific. Link to commits or `decisions.md` ADRs when context matters.

**Categories:** `Added` · `Changed` · `Fixed` · `Removed` · `Deprecated` · `Security`.

## [Unreleased]

### Changed (latest, native stereo capture)
- **A stereo pair now RECORDS as one interleaved stereo file**, not two mono files. When you arm a stereo track, capture writes a single 2-channel `Track_NN.wav` (named for the L slot) — drag it straight into your DAW as a stereo stem; there's no second mono file to reconcile. The pair still shows as one logical strip across MIXER / EDIT / PATCH.
  - **Recorder** opens one 2-channel writer for the pair and interleaves both inputs into it; backup + every N-way mirror copy the stereo file too; auto-split / RF64-past-4 GiB / pre-roll all account for both channels. The real-time meter + capture path are unchanged.
  - **Playback / virtual soundcheck** loads the one file as two routed channels (ch0 → L's output, ch1 → R's), so monitoring and console routing are identical to before.
  - **Bounce / export** of the pair reads both halves from the one file (`bounceStereoPairToWav`); **EDIT** shows true L-top / R-bottom lanes drawn from the file's two channels; **import** of an external stereo file likewise writes one interleaved `Track_NN.wav`.
  - **Old sessions still open**: a session recorded the previous way (two mono files) plays, edits, and exports exactly as before — the loader sniffs the file's channel count. See the 2026-06-13 ADR in `decisions.md`. Headless-tested (new "Stereo pair records ONE interleaved file + player routes both channels" case; 243 groups, 0 failures).
  - **Stereo clip editing stays in sync**: the per-clip right-click ops (lock / duplicate / delete / consolidate / **normalize**) now apply to **both** halves of a collapsed stereo pair, matching clip gain. Consolidating a stereo track keeps it stereo (each channel flattens to its own file) instead of dropping to the left channel. Normalize applies **one shared gain** to the pair (the most conservative across both channels, so the loudest lands at target and the stereo image stays balanced).

### Changed (stereo collapse — earlier)
- **An imported stereo file is treated as one stereo track everywhere.** A pair *behaves* as a single stereo track across every surface:
  - **Pan** — import spreads the pair **hard-left / hard-right** for the full stereo image (was centre/centre, which summed toward mono).
  - **Persistence** — the pairing is written to `session_mix.json` **immediately on import**, so it survives reopen instead of being RAM-only (the old behaviour re-split it into two mono strips via the recovery path).
  - **Meterbridge** — a pair collapses to **one stereo meter** (the L meter shows the R as its second bar; the "… R" column is gone).
  - **Export dialog** (*Export individual tracks*) — **one row per strip**, labelled "… (stereo)", mapped back to both physical channels.
  - **Export files** — a pair bounces/exports as **one interleaved stereo file**, not two mono stems: `TrackExporter::exportStereoPair` (per-track, with sample-rate conversion) and `AudioEngine::bounceStereoPairToWav` (edited-arrangement stem, streamed). Both export callers skip the R half when its L is handled.
  - The mixer already collapsed a pair into one strip with one stereo meter; this closes the pan, persistence, meterbridge, export-list, and export-file gaps. Headless-tested (`StereoExportTests` + a bounce-pair case in `AudioCallbackTests`).

### Fixed (latest, recorder)
- **De-flaked the `session.report.json` part-file enumeration** (~7% failure rate, 2/30 runs). `drainOnce()` (stopRecording's final flush and the test harness's `drainPendingForTests`) fans out to every shard, but each shard's own `TimeSliceThread` is *also* draining it — two readers on a single-reader `AbstractFifo` corrupted the part-file list, byte counts, and sample totals (the auto-split bookkeeping). Added a **per-shard drain lock** so concurrent drains of the same shard serialise; different shards still drain in parallel, and it never touches the audio thread. Also a latent production race in `stopRecording`'s flush, not just the test. 0/50 + 0/25 stress runs after.

### Added (capture-split Phases 1d + 2)
- **Out-of-process recording, behind a flag** (Session ▸ *Capture daemon (experimental)*, persisted; **default OFF until the 64-channel hardware soak passes**). When enabled, RECORD routes the take through the `zynforge-capture` daemon — the GUI keeps its own device open for monitoring/meters/playback, the daemon writes the files, so **a GUI crash can no longer stop a take**. New `CaptureSupervisor` (`Source/Capture/CaptureSupervisor.{h,cpp}`): discovers/launches the daemon binary, attach-first connect, drives the take over the wire, GUI-side watchdog.
- **Phase 2 semantics shipped with it:** quitting the GUI **leaves a rolling take recording** (`shutdown()` never stops a recording daemon; an idle daemon we launched is asked to exit via a new `Quit` protocol verb — which the daemon itself **refuses mid-take**). A restarted GUI **reattaches to the rolling daemon** on launch (attach-first; never spawns a twin) and adopts the take — STOP closes it normally. The watchdog reports a dead daemon once, **loudly when it died mid-take** (no silent auto-relaunch — the engineer must see it). All of this is headless-tested end-to-end against the **real binary**: launch → record → supervisor "dies" → reattach → take still rolling → stop → verified WAV on disk → wire-quit (`CaptureSupervisorTests`).

### Added (capture-split Phase 1c)
- **`zynforge-capture` — the headless capture daemon exists.** A second binary (`build/ZynforgeCapture_artefacts/Release/ZynforgeCapture`, console app, no UI) that owns the audio device + the `MultitrackRecorder` out-of-process and is driven entirely over the local-socket CaptureProtocol: Hello handshake, SetTrackCount / SetCaptureFormat / ArmTrack, StartRecording(sessionDir) / StopRecording, with a 10 Hz `EngineStatus` push to the attached client. **Capture-only by design** — playback commands are refused (`"daemon is capture-only; playback is GUI-side"`); the point is a GUI death never stops a take. Stops cleanly on SIGTERM/SIGINT (closes the take + manifest first); SIGPIPE ignored so a dropped GUI socket can't kill it. The daemon engine (`Source/Capture/CaptureDaemon.{h,cpp}`) links into the test suite with a no-device test mode: `CaptureDaemonTests` records a real WAV take driven entirely over the wire (configure → start → synthetic input blocks → stop → verify the file's audio) and asserts the playback refusal. **Not yet wired into the GUI** — that's Phase 1d (CaptureClient integration + flagged cutover + soak).

### Fixed (latest, stereo clip gain)
- **Clip gain on a stereo track rode only the LEFT channel.** The EDIT view's gain handle (and the clip context menu's gain presets + custom-dB prompt) applied `setClipGainDb` only to the row's own physical track. The collapsed stereo row's peer list (`editGroupPeers`) now always includes each stereo-L peer's R partner (dedup-safe with edit groups), so gain rides, fades and the other peer-routed clip ops hit both halves of the pair as one stereo clip.

### Fixed (latest, debug + audit pass)
- **EDIT view burned ~100% of a core at idle — now ~6%.** Two unconditional repaints: `TrackRow::setPlayheadX()` repainted **every waveform row on every timer tick even when the playhead hadn't moved** (transport idle), and the time ruler repainted unconditionally at its 4 Hz idle rate (re-shaping all its text labels forever). The playhead push is now change-gated, and the idle ruler repaints only when something it draws actually changed (seek, markers, loop, edit cursor, session length); while the transport rolls both repaint at full rate as before.
- **Idle CPU cut ~3× in MIXER view (14% → ~5%).** Profiling the idle app showed the message thread burning in repaints: the **VCA panel blanket-repainted all 8 mini-strips 20×/sec** (the engine-sync lived *inside* `paint()`, so the panel had to keep repainting to stay fresh) and **MasterStrip rebuilt its output ComboBox every 100 ms tick**. The VCA sync moved into a change-gated `syncFromEngine()` (repaints only when the shown dB/colour actually moves), and `refreshOutputs()` now skips its rebuild while the device count + stereo mode are unchanged. Remaining idle load is the live input meters, by design.
- **CaptureClient crashed on teardown after a server-side disconnect** (caught by the new supersede test — `std::terminate` in the destructor). When the *daemon* dropped the connection, the reader thread cleared `connected` itself; a later `disconnect()` then early-returned without joining the finished-but-joinable reader, and destroying a joinable `std::thread` terminates the process (it also reset the socket under the reader). `disconnect()` now always joins a joinable reader.
- **CaptureServer accept-loop wedge**: a second GUI connection used to block the accept loop until the first GUI disconnected on its own (join-before-close). A new connection now **supersedes** the old one (old socket closed first, then joined) — regression-tested. Self-join deadlock guards (debug asserts) added to `stop()`/`disconnect()` against calling them from the reader-thread callbacks.

### Added (latest, capture-split Phase 1 transport)
- **Local-socket transport for the capture protocol** (`Source/Network/CaptureLink.{h,cpp}`). `CaptureServer` (daemon side) listens on loopback, holds one GUI connection, reads `Command` lines and pushes `status`/`reply`; `CaptureClient` (GUI side) connects, sends commands, receives status. A persistent bidirectional newline-JSON connection with an auto-handled **Hello version handshake** (a mismatched GUI/daemon is acked not-ok, never silently mis-records). Write failures fail the call rather than the process (SIGPIPE already ignored). Still **transport only** — not wired to a recorder. Headless **loopback tests** (`CaptureLinkTests`): real `CaptureServer`+`CaptureClient` over 127.0.0.1 exercise the handshake, a GUI→daemon command, a daemon→GUI status push, and version rejection (0 failures across 15 stress runs).

### Added (capture-split Phase 1 foundation)
- **Capture daemon ↔ GUI wire protocol — the contract, built and tested ahead of the daemon.** `Source/Network/CaptureProtocol.h` defines newline-delimited JSON messages tagged `cmd` / `reply` / `status`: a `Command` control vocabulary (Hello, Start/Stop recording + playback, ArmTrack, SetCaptureFormat, SetSessionDir, Ping), `status` wrapping `EngineStatus`, and a **Hello version handshake** that fails *loud* on a GUI/daemon version mismatch rather than risk a silent mis-record. Header-only, engine-free, transport-free — tested in isolation (`CaptureProtocolTests`) the same way ConsoleLink's protocol was proven before any hardware. It's **deliberately not wired to the recorder yet**: a half-built capture split that owns recording would *reduce* reliability, defeating the purpose. The remaining Phase-1 chunks (socket transport → `zynforge-capture` binary → GUI client → flagged cutover) are scoped in `decisions.md` + `tasks.md`.

### Added (latest, status boundary — capture-split Phase 0)
- **Canonical, serialisable `EngineStatus` snapshot** (`Source/Audio/EngineStatus.h`) — transport, position/elapsed, disk MB/s + last-write + minutes remaining, missed samples, CPU load, ring-buffer fill, BS.1770 loudness, format, and per-track {name, peak, rms, arm/mute/solo/monitor, stereo, colour}. `AudioEngine::captureStatus()` fills it at one chokepoint; it round-trips through JSON. This is Phase 0 of the capture-process split (see `decisions.md`): consumers read one struct instead of reaching into recorder/engine internals, and the same boundary works across a future process split. Two consumers migrated onto it so far: the **companion server's `/state.json`** (de-duplicating its direct-internal reads; same shape the web client consumes) and the **header readouts** — the PerfDashboard (CPU/disk/buffer/missed) and the BigClock loudness/disk feed now read one per-tick snapshot instead of a dozen scattered engine getters. Headless-tested (`EngineStatusTests`).

### Changed (latest, console link)
- **Console virtual-soundcheck control is now profile-based, not X32-only.** The connect dialog has a **console picker** (Behringer X32 / Midas M32, DiGiCo SD/Quantum, Yamaha CL/QL/RIVAGE, SSL Live, Allen & Heath dLive/Avantis/SQ, Generic OSC). `ConsoleLink` is now a transport + state machine driven by a pluggable `ConsoleProfile` (`Source/Network/ConsoleProfile.h`); each profile declares its capabilities honestly. The **X32/M32 profile** keeps full OSC control (repatch + head-amp gain capture). The large-format desks ship as **native-VSC profiles** — ZynForge records and plays their record card and the console's own Virtual Soundcheck does the repatch (those desks use non-OSC control or have no OSC repatch), so the per-input repatch/gain menu items grey out and the status line points you at the console. Per-console over-the-wire control (e.g. Yamaha SCP/TCP) is a tracked follow-up that needs a second transport layer + hardware. See `decisions.md` *Console VSC control is profile-based*. Headless-tested (`ConsoleLinkTests` gains a profile-capability case).

### Fixed (latest, EDIT playhead)
- **The EDIT time-ruler playhead and the waveform-lane playhead now line up.** They drifted a few pixels apart (offset `4 − 8·position`, so right at the start, crossing in the middle, left at the end) because the wave lanes inset their clip content by `brand::space::xs` (4 px each side) and mapped the playhead across `waveW − 8`, while the ruler mapped time across the full pane with no inset. The ruler's ticks, markers, and playhead now route through shared `rulerPxPerSec` / `rulerTimeToX` / `rulerXToTime` helpers that bake in the same 4 px inset. The lane playhead also now maps across the rows' content width (`list->getWidth()`) instead of the EditPage's visible width, so the two stay aligned when zoomed in as well.

No more coarse jumps; the master's scroll is re-enabled because a deliberate 0.5 dB trim can't yank it like the old default could.

### Fixed (master strip)
- **The master fader's value box no longer collides with the etched "ZYNFORGE" maker's mark.** `MasterStrip::resized()` laid the meter + fader (whose value text box shows e.g. "0.0 dB") all the way to the plate bottom, but `paint()` stamps the etched wordmark into the bottom 15 px — so the two overlapped. `resized()` now reserves that mark band (shared `kMarkBandH` constant keeps paint + layout in sync).

### Fixed (latest, console link)
- **Console reconnect was silently broken.** Disconnecting from the desk and connecting again failed without explanation: `juce::DatagramSocket::shutdown()` permanently invalidates the socket handle (sets it to −1, never reopened), so re-binding the reused socket always returned false. `ConsoleLink` now creates a fresh `DatagramSocket` on every `connect()`. Regression-tested with a real connect → disconnect → reconnect cycle (the test fails on the old code).
- **Capturing head-amp gains while the desk is unreachable no longer wipes the saved capture.** `captureGains()` clears the in-memory gains before polling; if no replies come back, the delayed auto-save now skips writing rather than overwriting a good `console_state.json` with an empty one.

### Added (latest, console link)
- **One-tap soundcheck repatch + head-amp gain capture for X32 / M32** (Session ▸ *Console: …*). Connect to the desk over OSC (UDP 10023), then: **SOUNDCHECK patch** first *queries* the console's four input-routing blocks and stashes whatever the show patch is (analog, AES50 stage boxes — no assumptions), then flips them to the card returns; **back to STAGE** restores the stashed patch verbatim. **Capture head-amp gains** polls `/headamp/NNN/gain` for every strip and saves them (with dB values) into the session's `console_state.json`; **restore head-amp gains** writes them back to the desk — recall the preamps to exactly where they were on show night, so virtual soundcheck hits the console at show levels. Stashed patch + gains survive to VSC day with the session and reload on connect. Refuses to "restore" a stage patch it never captured. Every message format is unit-tested against the public X32 OSC protocol through a transport seam (`ConsoleLinkTests`) — no console needed for the suite.

### Added (latest, deliverables)
- **Detect songs → markers** (Session ▸ *Detect songs → markers…*). Scans the recorded tracks after the show and drops a named marker ("Song 1…n") at every song start, so next-day virtual soundcheck is "jump to song 4" instead of scrubbing a 2-hour timeline. Live-aware detection: naive silence detection fails on live recordings (ambient/vocal mics stay hot with crowd noise between songs), so each track gets its own 100 ms peak envelope and a moment counts as *music* only when **at least 2 tracks are active at once** — the band lights up many channels simultaneously, applause on a couple of mics doesn't. Short dips inside a song (< 4 s) don't split it; runs shorter than 60 s aren't songs. Rename the markers from the Marker List. Headless-tested (`SongDetectorTests`, incl. the hot-ambient-mic case).
- **Post-show QC report** (Session ▸ *Post-show QC report…*). Scans every recorded track in the background and pops a sortable table — **peak dBFS**, **BS.1770 integrated loudness**, **clipping events** (flat-top runs ≥ 3 samples at ≥ 0.999 FS, each with its timecode), and the **between-song noise floor** (10th percentile of 100 ms RMS windows). Click the *Clips* column header and the problem channels float to the top. A plain-text report (`Export Files/QC Report <stamp>.txt`) is written alongside, including the recorder's missed-samples count from `session.report.json` — "channel 23 clipped 4 times during song 6" is now a 10-second lookup the morning after. Streamed analysis (never loads a track into RAM); headless-tested (`QcAnalyzerTests`).

### Added (latest, show readiness)
- **Crash telemetry on launch.** If the app crashed since the previous run, the next launch surfaces it: a notice with the report's timestamp, exception type/signal and termination reason, plus **Copy details** (paste-ready for a GitHub issue) and **Reveal in Finder**. First run sets a baseline silently; nothing pops on a clean history. (`Source/Audio/CrashReportScan.h`, headless-tested.)
- **Pre-flight checklist now *measures* the rig instead of reading config.** New probes on top of the existing snapshot: **measured disk write speed** of the session volume (streams a 16 MB probe file and times it) vs. the throughput the armed channel count × format actually demands, with a 1.5× jitter margin; **every mirror drive verified mounted *and writable*** (a real create-write-delete probe, not `isDirectory()`); **live CPU callback load** (green < 50 %, amber < 80 %); **session-vs-device sample-rate mismatch** (catches the wrong-pitch virtual soundcheck before the band hears it); and **signal presence on armed inputs** (N of M armed channels showing > −60 dBFS at line check). Probes live in `Source/Audio/PreflightProbes.h`, headless-tested (`PreflightTests`, suite now 202 groups).

### Changed (latest, memory)
- **Bounce / consolidate / stereo-mix renders now stream to disk in 64k-sample windows** instead of materialising the whole arrangement in RAM. Bouncing stems or the stereo mix of a multi-hour show previously allocated one flat buffer per track (a 3-hour mono track ≈ 2 GB) plus a full-length stereo buffer for the mix — long sessions could push the app into multi-GB territory or hit the 2³¹-sample buffer cap. The render core (`forEachArrangementWindow` / `forEachStereoMixWindow`) now hands fixed windows straight to the 24-bit WAV writer, so bounces run in a few MB regardless of show length, and **Consolidate** writes only the selected range without rendering the whole track first. Output is sample-identical (the window size is a multiple of the 512-sample automation step). Same audio, flat memory.
- **Tab-to-transient analysis no longer loads 30 minutes of audio per track.** The transient-cache build read up to ~345 MB per track into one buffer; it now scans in overlapped ~60 s chunks (~12 MB), with identical onsets.
- **Cross-track clip readers are pruned when nothing references them.** Every Consolidate / cross-track paste opens a buffered reader for its file; superseded ones used to stay open (buffer + file handle) until the session closed. They're now released as soon as no clip on any track uses the file.

### Fixed (latest, tests)
- **De-flaked the volume-automation playback test.** "Volume automation attenuates the playback output by position" failed intermittently (~1 in 3 runs) under no code fault. The player reads through a `BufferingAudioReader` that buffers a window around the *current* position on a background thread; the test warmed the buffer at position 0, then seeked to sample 40000 to read the attenuated tail, then seeked **back** to 0 to measure the loud head — by which point the buffer window had moved to 40000, so the head read sometimes returned silence and the `high > 0.20` assertion flaked. Reordered so the loud head is measured **first**, while the buffer is still warm at 0, then the tail region is warmed with a short re-seek loop before the quiet sample is measured. 6 consecutive full-suite runs now pass clean (198 groups, 0 failures). No production-code change — test-only race.

### Fixed (latest, companion)
- **"Start companion server on :9000…" now actually works** — it was **dead code**. The menu item used id 270, which falls inside the `menuItemSelected` dispatch range `261..289` (template-as-default), so every click was routed to the *template* handler and the companion code never ran — the server never started, nothing was copied to the clipboard, and there was no error. Moved the companion item to id 950 (and the new Auto-Save & Backup item, which had the same latent issue at id 283, to 951) — both now outside every dispatch range. Added a regression guard to `MenuDispatchTests` that fails if a marquee static item's id lands in a dispatch range, plus a logged reason when a bind fails.

### Added (latest, safety)
- **Auto-save + full backup-session, with a configurable interval.** Session ▸ **Auto-Save & Backup…** opens a picker — **Off / 1 / 2 / 5 / 10 / 15 minutes** (default 5). When on, the app periodically writes the session (mix, cues, automation, layout) to disk **and** drops a complete **backup session** into the session's own `Session File Backups/` folder: a timestamped sub-folder `<Name>_<stamp>/` holding a copy of every file that defines the session (`.zfproj`, `session_mix.json`, `session_settings.json`, `markers.json`) — everything needed to restore it, **excluding** the immutable multi-GB audio (which lives once in `Audio Files/`; to restore, copy the snapshot's files back over the session root). Keeps the 10 newest. It only writes when something actually changed since the last save (tracked via the undo stack), so it never churns identical backups, and it sits quietly in the footer (`Auto-saved HH:MM:SS`) rather than popping a toast. Every manual Save and cue edit drops the same full backup session now, too. Recordings remain saved live and independent of this — a take is never at risk either way. (Backup logic is `Source/Audio/SessionBackup.h`, headless-tested.)

### Changed (latest, capture)
- **Post-stop integrity hashing is ~100× faster.** The `session.report.json` SHA-256 manifest used to hash recorded audio with a portable software SHA at background QoS — an overnight 2-track / 8.6 GB take took ~8 minutes to finish hashing. It now (a) uses the CPU's **hardware SHA extensions** via `CC_SHA256` (ARMv8 crypto / SHA-NI), (b) **hashes files in parallel**, and (c) runs at **utility QoS** (still yields to the UI/next take, but isn't throttled to a trickle). Measured on the real 4.31 GB take: ~2.8 s/file in hardware vs ~480 s for the pair before — and both files now run concurrently. Digests are byte-identical to `shasum -a 256`, so the manifest stays verifiable with standard tools (`tools/verify_take.sh` unchanged). Validated against the canonical FIPS-180 vectors + `juce::SHA256` across buffer boundaries.

### Fixed (latest, companion security)
- **Companion client now sends its access token on every request — including the audio stream.** Under the token regime the served page still hard-coded `/state.json`, `/cmd` and `<source src="/stream.wav">` with no token, so once you opened `/?t=<token>` every follow-up request 401'd — the strips, transport, and remote-audition stream were all locked out. The page now reads the token from its own URL and threads it onto each sub-request; since an `<audio>` element can't set an `Authorization` header, the stream carries `?t=<token>` in its URL. So **`/stream.wav` is now properly access-controlled** (no token → 401), not open and not broken. Transport confidentiality is still delivered by fronting loopback with a tunnel (no in-app TLS — see `decisions.md`). Locked by a headless integration test that drives the real server on loopback.

Genuine failures the engineer must act on — disk full / out of space, audio device lost, a write that couldn't complete — now flash red instead of amber-or-grey, so they read as danger even at the edge of vision. `showStatus()` routes by message severity automatically.
- **Documented the component system** — `design.md` now carries a *Component Reference* with the state × variant matrix for every interactive component (Button, Toast, Channel strip, Fader, LED/Meter, Dialog), so the system is documented as a system, not just enforced in code.

### Changed (latest, design system)
- **Closed the last token-bypass gaps** (full `/design-system` audit): the strip-silence dialog was the one place bypassing *both* the colour and font tokens (raw `Colour::fromRGB` + raw `juce::Font`) — now `brand::textPrimary` + `brand::type::uiBody()`. The two unused type-scale rungs (`subhead`/`display`) are annotated as reserved continuous-scale steps. Result: **zero** raw colours/fonts/uncatalogued alphas outside the theme layer.

### Added (latest, control surfaces)
- **MCU surface: master fader, jog-wheel scrub, and 7-segment time display** — the Mackie/FaderPort surface now drives more than the 8 channel strips. ### Fixed (latest)
- **Volume automation now actually affects the audio outputs (it only touched the stereo monitor mix before)** — the real reason "nothing changed": playback has two summing paths — the per-track **routed hardware outputs** (Out 1-2 etc., plus aux sends and the stream bus), and a separate **stereo monitor mix**. Automation was only read into the monitor mix; the routed-output path used `effectiveGainDb` (static fader + VCA only), so any session monitored through its assigned outputs played at the fixed fader level and a drawn volume curve did nothing audible. `effectiveGainDb` now folds in the volume-automation value at the playhead during playback, so the per-channel outputs, aux sends, and stream bus all follow the curve (stereo pairs read the left track's lane). Combined with the readout fix below, a volume move is now both visible and audible on the actual outputs.
- **Volume/pan/mute automation now reads back on the EDIT lane readout, and applies to both halves of a stereo pair** — drawing a volume curve worked at the engine level (the audio callback already read the lanes during playback), but it *looked* dead: the lane's value readout (e.g. "vol 0.0 dB", pinned top-right) and the value indicator line were hard-wired to the **static fader value**, so they never moved as the curve played — making automation feel like decoration. They now follow the automation value at the playhead during playback (and show the live fader value when stopped). Separately, a stereo pair stores its automation only on the LEFT track, but the audio callback applied gain per physical channel — so the RIGHT half ignored the curve and a volume move barely dented the (still full-level) stereo sum. The right partner now reads the left track's volume + mute lanes (pan stays per-channel so the stereo image isn't collapsed), so a move you draw is fully audible.
- **EDIT waveforms were frozen at the first ~0.1 s of each take (root cause of the "blocky" waveform)** — the real bug behind the chunky, low-detail waveforms: while recording, the EDIT view pushed a fresh `FileInputSource` into every track's `AudioThumbnail` on each 24 Hz timer tick to "grow" the waveform. But `AudioThumbnail::setSource` first consults the `AudioThumbnailCache` by file hash and, finding an entry that reports itself fully loaded, returns it *without re-reading the file*. The very first tick read each WAV when only a fraction of a second (~5120 samples) had been written, cached that tiny partial as "complete", and every later tick — and the final post-stop render — reused it. So a 3-minute take drew as ~40 stretched min/max blocks, and the partial was even persisted into `WaveCache.wfm`, poisoning reopen. Fixes: (1) the reload path now drops the stale cached thumb (`removeThumb`) before re-reading, so the finished file is scanned at full length; (2) waveforms are no longer re-scanned from disk *during* recording at all — 48 channels re-reading at 24 Hz contended with the recorder's own capture writes (a dropout risk on a live recorder) — instead a single clean full re-scan runs the moment recording stops, when the files are final; (3) the `WaveCache.wfm` version revision was bumped so existing poisoned caches are discarded and re-scanned from the now-complete WAVs.
- **EDIT waveforms are sharper, regenerate when stale, and no longer blow idle channels into bars of noise** — three causes: (1) the `AudioThumbnail` resolution was `1024` samples-per-point (~21 ms @ 48 kHz), so zooming in just stretched coarse min/max blocks into flat-topped rectangles — dropped to **128** for 8× finer detail; (2) the on-disk `WaveCache.wfm` bakes thumbnails at the resolution they were built, and `loadCacheFromSession` restored that coarse data by file hash, so the finer resolution never took effect on a previously-recorded session — the cache file now carries a versioned header (magic + resolution) and a mismatch (including pre-header caches) deletes the stale file and forces a fresh re-scan at the current resolution; (3) the amplitude auto-fit (`0.85/peak`) was capped at **64×**, which on a big session amplified every quiet/unused input's noise floor to full lane height and made the V+/V- buttons feel inconsistent (a quiet channel was already pinned at max, so it didn't respond). The auto-gain now caps at **4×**, treats anything below ~-48 dBFS as silent (clean flat line, no boost), and vertical zoom always multiplies on top so V+/V- have a visible, predictable effect.
- **Every dialog now uses the grey ZynForge chrome (10 were still JUCE-default navy)** — only 6 of the 17 `AlertWindow` prompts set the per-window LookAndFeel; the rest (New marker, Clip gain, Rename take, Rename marker, Cue name, Mirror host, Cloud upload command, Quick-start tour, User guide, Save template, Pre-flight checklist) rendered in JUCE's default navy, violating the standing "all prompts grey + light grey" rule. All 17 now set the grey chrome at construction (via the owning component's LookAndFeel), so prompts are visually consistent app-wide.
- **Clip lock is now enforced in the engine for delete + duplicate, not just hidden in the menu** — a locked clip already refused trim / move / fade at the engine level, but `deleteClip` / `duplicateClip` only checked the lock by *disabling* those right-click menu items. Any other call path (e.g. a future keyboard shortcut) could have deleted or duplicated a locked clip. Both engine ops now refuse a locked clip outright, matching trim/move/fade. No internal caller is affected (crop/split rebuild clips directly rather than going through these). Test extended to assert delete + duplicate are refused while locked and succeed after unlock.
- **Deleting the last clip on a track now silences it (was reverting to whole-file playback)** — the player treated an empty clip list as the lazy "play the whole `Track_NN.wav`" default, which is correct for a track that's never been edited but wrong once you've deleted everything off it: the track would suddenly play its full original file again instead of going quiet. `SessionPlayer` now tracks, per track, whether the engine has *explicitly* set a clip list; an explicit-but-empty list renders silence, while a track the engine never set clips for still falls back to whole-file (so untouched tracks keep playing). - **Split did nothing after opening an audio folder (wrong subsystem guard)** — `splitTrackAtPlayhead` bailed out when `track >= recorder.getNumTracks()`, but opening an existing session/audio folder loads the *player* (which holds the tracks + files) without sizing the *recorder* (the capture side), so its count stayed 0 and every split was silently refused even though the audio was right there. The guard now bounds against whichever subsystem knows about tracks (recorder OR player); the existing on-disk `Track_NN.wav` existence check remains the real gate. Verified by a new file-backed end-to-end test (`Clip split + crop`) that records a real take, loads it, and asserts split produces two timeline-adjacent, file-contiguous clips that round-trip through undo. (Recording-then-editing in the same session already worked, since arming sets the recorder count.)
- **Clip edits were silently lost on save/reload and ignored by undo (active-take desync)** — every live clip edit (split / trim / move / fade / gain / mute / lock / delete / duplicate) mutated the live `trackClips` list the player renders, but never mirrored the result into the active Take. Since `.zfproj` persistence and the new clip-aware undo both serialise the *Take* (`playlistsToJson`), the edits never reached disk and undo's before/after snapshots came out identical — so reopening a session dropped all comping work and Cmd+Z was a silent no-op for everything except Crop (the only path that happened to mirror). Root cause: the documented "active take == trackClips" invariant was only upheld by `cropToRange`. Fix: a single `AudioEngine::syncActiveTake(track)` helper now mirrors the live clips into the active take (creating Take 1 if none) and is called at the end of every mutator. New headless regression tests (`Clip edit persistence/undo`) assert that an edit actually changes `playlistsToJson` and round-trips through undo/redo.
- **Recordings no longer corrupt under multi-channel load (writer-thread race)** — the recorder drained its per-channel FIFOs to disk across a *pool* of writer threads. Under real parallelism this corrupted captures: whole channels came back as white-noise garbage, non-deterministically, worse with more channels (this is the "weird form" / glitchy takes). Disk writing is now serialised on a single thread — more than enough for the I/O load (~6.6 MB/s for 48ch/24-bit/48k) — which a new headless integrity test (`RecordingIntegrityTests`, run via `--run-tests`) proves clean across 8/16/48-channel captures (and which reproduced the bug at 2+ threads). See `decisions.md` "Single writer thread for capture".
- **Recordings were truncated / glitched (stop-time data race)** — `stopRecording()` did its final FIFO flush and closed the writers on the message thread *while the shard writer threads were still draining*. That meant two consumers on each single-consumer FIFO and `writers.clear()` freeing an `AudioFormatWriter` mid-`writeFromFloatArrays`, which corrupted samples and truncated files at random per-channel lengths — yet each WAV header kept the full intended sample count (header said 24 s, the data was 8 s), so players read past the real audio into garbage and the takes sounded glitchy / unclear. Fix: detach the shard clients from their writer threads (which blocks until any in-flight drain finishes) **before** the final single-threaded flush + close, then re-attach for the next take. All armed tracks now finalize at the same correct length.
- **Patch page is now scrollable (both axes)** — the INPUT / OUTPUT PATCH grid painted rows/columns at a fixed offset with no way to reach hardware channels past the window bottom or strips past the right edge, so on a high-count interface (e.g. a 64/128-channel Dante card, or many strips) you couldn't see or patch them. - **Crash on quit (static font teardown)** — quitting the app could `terminate()` during `__cxa_finalize`: the BrandTokens font cache (a function-local `static std::unordered_map<size_t, juce::Font>` plus ~14 `static const juce::Font` role accessors) and the LookAndFeel's `static juce::Typeface::Ptr` faces were destroyed *after* JUCE tore down CoreText, so their CoreText typeface destructors fired into a dead framework. Fix: the font cache is now cleared from `JUCEApplication::shutdown()` (while CoreText is alive), the role accessors route through that clearable cache instead of holding their own statics, and the LookAndFeel's bundled typefaces are now members (released when the LookAndFeel dies during shutdown).
